# Config outranks the derived collection; the floor, not a probe, guarantees the flag

[Issue #105](https://github.com/sripwoud/pi-memsearch/issues/105): pi passed its derived collection as `-c`, the highest-priority source in memsearch's config chain, so a `[milvus].collection` in `~/.memsearch/config.toml` or a project `.memsearch.toml` never took effect for pi. Upstream [#726](https://github.com/zilliztech/memsearch/pull/726) (first released in v0.4.20) added `--default-collection` and moved every stock plugin onto it. Upstream now documents pinning one collection in config as _the_ way to share memory across worktrees ([#717](https://github.com/zilliztech/memsearch/issues/717)). Pin two worktrees and the mesh read the pinned collection while pi read its own: the silo ADR 0001 exists to prevent.

pi now passes the derivation as `--default-collection`, and reads back the name memsearch resolves with `config get milvus.collection --default-collection <derived>`. Anything that reports or compares a collection uses that resolved name.

- **Raise the floor, do not probe.** The stock plugins ship `memsearch_supports_default_collection` and refuse collection operations against an older core. They cannot choose the user's core, so refusing is their only lever. pi installs its own core through `MEMSEARCH_SPEC`, so a `>=0.4.20` floor makes the flag always present, and a probe would be dead code. Porting it would also have refused every collection operation for anyone on the old `>=0.4.17` floor. This diverges from the mesh on mechanism and converges on behavior, which is what ADR 0001 asks for. Do not "restore parity" by adding the probe.
- **Report the resolved name, never the derived one.** Considered alternative: pass the flag but keep displaying the derivation, which saves one subprocess. Under a pin that is wrong in exactly the way [#73](https://github.com/sripwoud/pi-memsearch/issues/73) was: `memory_status` naming a collection the session does not read. The lookup is memoized per directory and default name, so it costs one subprocess per directory per process.
- **Foreign projects resolve at their own directory, then go explicit.** memsearch children run at the session's repository directory, and memsearch reads `.memsearch.toml` from the working directory. A `--default-collection` sent for a discovered project would therefore be outranked by the _session's_ project pin. So a discovered project's default is resolved by `config get` run at that project, then searched as `-c <resolved>`. Cross-repo dedup keys on resolved names, so projects pinned to one collection collapse.
- **The sidecar layers, it does not look up.** Auto-context sends the derived name as `default_collection`, and the sidecar applies memsearch's own `resolve_config(default_overrides=…)`. That is one code path with the CLI and adds no subprocess per prompt.

Not migrated: a user who already had a pin sees pi move to the pinned collection. Chunks in the previously derived collection stay behind, and the next index refills the pinned one from the markdown store.
